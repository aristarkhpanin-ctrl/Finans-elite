## Календарный план и бюджетирование по этапам (паритет с PE) — завершено (K0–K7)

- Аналог «Инвестиционного плана» PE: `calc_core/models/calendar.py` (`Stage`/`Resource`/
  `CalendarPlan` → `InvestmentPlan.calendar`), `calc_core/engine/calendar.py`. Этапы: тип
  (`expense`/`asset`/`production`), сроки, связи-предшественники (финиш→старт), иерархия групп,
  стоимость (прямая или Σ ресурсов с задержкой оплаты → `B23`), тайминг `uniform`/`on_finish`.
- Трактовка: обычный → `C15` (сразу `I21` либо РБП `B15` со списанием); актив → синтетический
  `Asset` (реюз машинерии, как выкуп лизинга); производство → старт продукта
  (`SalesLine.start_month`). **Пустой календарь инертен → golden без дрейфа чисел.**
- Выход — смета `CalcResult.budget` (свёртка групп + помесячный график). API
  `GET /projects/{id}/budget`; UI — вкладка «Календарный план» (Гантт, ресурсы, живая смета;
  чистая логика `frontend/.../calendar.logic.ts` — зеркало движка). Методика/решения —
  `docs/CALENDAR-PLAN-DECOMPOSITION.md`, `docs/RESEARCH-CALENDAR-PLAN.md`.
- **Бюджетный разрез сметы (взгляд финдиректора).** `Budget` несёт не только начисление:
  `monthly_cash` (оплата со сдвигом на отсрочку ресурсов — общий помощник `_payment_graph`
  с отчётами, разойтись не могут), `cumulative`/`cumulative_cash` (S-кривые), `payables`
  (начислено − оплачено = **та же величина, что B23**) и разбивку по трактовке
  `expense_total`/`deferred_total`/`asset_total` (куда стоимость попадёт: I21 / B15 / B14).
  У строки этапа — свои `monthly`/`monthly_cash` и `treatment`; **смешанной группе трактовка
  не приписывается** (`mixed`). UI — `BudgetGantt.tsx`: полоса красится **по трактовке**,
  под ней пунктиром полоса оплаты (видна отсрочка), нижняя панель — деньги по периодам
  (освоение · оплата · накопленная оплата · не оплачено), масштаб месяц/квартал/год
  (свёртка — реюз `periodChunks`; потоки суммируются, уровни — на конец периода).
  Связи «финиш → старт» — стрелки (`linkPath`: прямой путь либо обход между строками при
  нулевом/отрицательном зазоре; этап внутри свёрнутой группы «переезжает» на неё).
  Перетаскивание полос — чистая `applyDrag` (тело — сдвиг, края — начало/длительность;
  ограничения модели `start_month ≥ 0` и `duration ≥ 1` соблюдаются в ней, а не в UI).
  **Группа не тянется** — её сроки свёрнуты из потомков. Во время перетаскивания смета и
  расписание считаются по предпросмотру, а модель правится один раз на отпускании.
- **Зеркало не может разойтись с движком.** Общая фикстура
  `frontend/src/fixtures/calendarBudget.json` генерируется
  `backend/scripts/dump_calendar_fixture.py`; её свежесть стережёт `test_calendar_fixture.py`
  (устарела → падает, как снимок OpenAPI), а `calendar.fixture.test.ts` прогоняет тот же
  вход через `calendar.logic.ts` и сверяет выход. Правка методики сметы: перегенерировать
  фикстуру → фронтовый тест падает, пока зеркало не обновлено. Эталон обязан задевать все
  правила (трактовки, отсрочку, актив без отсрочки, группу, связи) — это отдельный тест.

## Доинвестирование в актив (пакет №8, gap 1.6) — завершено (AD0–AD2, 0.9.32)

- `Asset.additional_investments: list[AdditionalInvestment(month, amount)]` — модернизация:
  доп. вложение капитализируется (C14 с НДС) и амортизируется от **остаточного срока**
  (`purchase + life − month`). `_assets` переписан на **слоистую амортизацию**: базовый слой
  (`cost/life`) + слой на каждое вложение (`amount/остаток`), все слои заканчиваются вместе
  с активом. Амортизация периода = Σ ставок активных слоёв; остаточная стоимость и выбытие
  при продаже — Σ по слоям; земля слои не амортизирует. **Актив без доинвестиций = один
  базовый слой → числа как прежде** (рефактор проверен: не-версионный дифф golden пуст).
  Бамп 0.9.32; поле пустое по умолчанию. Методика — SPEC §9; план —
  `docs/ADDITIONAL-INVESTMENT-DECOMPOSITION.md`. UI — блок в карточке актива (AssetsTab).

## НМА как класс актива (пакет №8, gap 1.8) — завершено (IA0–IA2, 0.9.36)

- `AssetCategory.INTANGIBLE`: НМА амортизируется как оборудование (I17), остаточная
  стоимость → `B16` (Другие активы; отдельной строки НМА в B1–B34 нет), **вне базы налога
  на имущество** (база — B13+B14). Реюз всей машинерии активов (capex→C14 с НДС,
  амортизация→I17/B10, продажа, доинвестирование). `b16 = nbv[INTANGIBLE]` в balance_leaves;
  B16 входит в B11→B20. Без НМА `B16=0` → golden только строка версии (бамп 0.9.36). UI —
  «НМА» в селектах группы ОС (AssetsTab, CalendarTab). Методика — SPEC §9; план —
  `docs/INTANGIBLE-ASSETS-DECOMPOSITION.md`.

## Детализация стартовых ОС (пакет №8, gap 1.7) — завершено (SO0–SO2, 0.9.37)

- Пред-существующий актив = `Asset` с `purchase_month < 0` (куплен до старта). Капвложений
  в горизонте нет; остаточная стоимость на t=−1 (`_preexisting_net_open`: `cost −
  ставка·min(−purchase_month, life)`; земля — по стоимости) **сворачивается в стартовый
  актив** (проверка сходимости стартового баланса + `opening_balance`), пользователь
  балансирует её капиталом/прибылью. С t=0 актив доамортизируется обычной машинерией
  (nbv→B14, амортизация→I17), может быть продан. Активы с `purchase_month ≥ 0` дают нулевую
  поправку → числа как раньше (golden только строка версии, бамп 0.9.37). Методика —
  SPEC §9; план — `docs/STARTING-ASSETS-DECOMPOSITION.md`. UI — подсказка к «Месяцу приобретения».

## Ставка дисконтирования по валюте (пакет №8, gap 1.4) — завершено (FC0–FC2, 0.9.38)

  показателей дублируется во второй валюте — `_metrics_foreign` пересчитывает чистый поток

## Второй продукт — «Финанс-Аудит» (проверка фирмы-цели по её отчётности)

- Платформа несёт **два продукта**: «Финанс-Элит» (бизнес-план, `calc_core`) и «Финанс-Аудит»

  Спецификация — `docs/FINANS-AUDIT-SPEC.md`, планы — `docs/FINANS-AUDIT-DECOMPOSITION.md`
  (этапы A–H) и `docs/FINANS-AUDIT-UI-DECOMPOSITION.md` (фазы 0–7 перехода на макеты).

- **Тарифы — свой каталог на каждый продукт** (`plans.py`): продукты продаются порознь,

  **точные стили — в `renderVals()`**, палитра — из объекта, который **возвращает** `THEME()`.
  Как и у первого продукта: в прод не переносятся, импортов из `docs/design/**` в `src/**`
  быть не должно. Хендофф собран против дерева, где кода аудита ещё не было, и описывает

  Лендинг (`docs/design/finans-audit/landing/`) — отдельный статический сайт вне
  `frontend/src`, в фазы не входит.
- Готово: **Фаза A** (каркас/тема/переключатель), **Фаза B** (`audit_core` модель субъекта/

  **Все фазы A–H закрыты.** Из v2 сделано: **свои нормативы показателей**

  оговорка об этом выводится), **помесячная периодичность** (`kind="month"`; `_PERIOD` в
  `analysis.py` — одна карта «тип → (дни, множитель к году)», множитель задан явно 1/4/12 →
  месяц ровно ×12, без накопления ошибки),

  та же выгрузка на своде группы), **сохранённые группы предприятий** (таблица
  `audit_groups` + миграция `c3d5e7f9a1b2` с RLS; API `/api/v1/audit/groups`, свод —
  `…/{id}/analyze`; хранится **состав, а не результат** → числа всегда по текущей
  отчётности; удалённый участник не исчезает молча — назван в оговорке и
  `missing_members`, имя хранится как «надгробие», группа без живых участников даёт
  пустой свод с оговоркой, а не ошибку) и **классическая модель Альтмана** для публичных
  компаний (рыночная капитализация — memo-строка `M_MARKET_CAP`; модель показывается
  **только при введённой капитализации** — у непубличной компании её не существует, и
  балансовый капитал вместо рыночного не подставляется; при своде группы капитализация
  **не складывается** — `MEMO_SUM_CODES`, иначе двойной счёт), **переоценка статей**
  (`AuditSubjectModel.revaluations` → `audit_core/revaluation.py`: у каждой поправки
  корреспонденция в капитале — актив `+Δ` растит капитал, обязательство `+Δ` уменьшает, —
  поэтому актив=пассив держится сам; переоценка **не бывает молчаливой**: оговорки с
  суммой и причиной, флаг `revalued` в результате, пометка в UI/DOCX/XLSX; капитал
  переоценке не подлежит; исходная модель не меняется, пустой список инертен; в своде
  переоценки участников применяются до сложения) и **основа отчётности**
  (`reporting_standard: rsbu|ifrs|management`) — **признак, а не трансформация**: форма
  ввода агрегатная и одинаковая для любого стандарта, поэтому «режим МСФО» был бы
  имитацией; основа попадает в шапку DOCX и **не даёт молча смешать** участников свода
  с разными основами. **Направления v2 закрыты**; остальное — в декомпозиции.

## Финанс-Аудит: ядро due diligence (фазы 0–7 перехода на макеты) — завершено

- **Каждый пакет — чистая функция над `AuditResult`, а не его расширение.** Слой читает
  готовый результат (и модель), возвращает свой объект и **в снимок аудита не входит** →
  `golden_audit` за все семь фаз не сдвинулся ни разу. Тот же приём, что «ревью плана»
  у первого продукта. Модули: `flags` (реестр находок), `earnings` (нормализация прибыли),
  `obligations` (реестр обязательств и залогов), `procedures` (чек-лист 28 процедур),
  `summary` (вердикт дела), `valuation` (DCF + мост EV → цена), `risk` (торнадо +
  Монте-Карло), `planfact` (прогноз продавца против факта), `compare` (сравнение дел).
  Методики — приложения И–У в SPEC; на каждое правило свой тест (срабатывание + тишина).
- **Конвейер один — `audit_core/pipeline.py::review_case(model) → CaseReview`.** Порядок
  слоёв строгий (обязательства → находки ввода → флаги → прибыль → процедуры → оценка →
  риски → план-факт → сводка), и он записан **в одном месте**: раньше копий было две, и
  во второй половина слоёв отсутствовала — документ молчал о находках. Экран, DOCX и
  XLSX идут из одного разбора; инвариант закреплён тестом.
- **Правило дома: пробел называется, а не заполняется.** Величина без входных данных —
  `None`, а не ноль; флаг без денежной меры — «меры нет», а не 0 ₽; непосчитанный раздел
  печатает **препятствия**, а не нули; у каждого слоя есть список `not_computed`, и он
  доходит до экрана, документа и файла. Сумма оценённых флагов **никогда** не называется
  скидкой к цене, забалансовые обязательства **никогда** не складываются с балансовым
  долгом, числа Монте-Карло идут с условием их чтения. Отказы, принятые осознанно
  (24 автопроцедуры по первичным документам, сценарии с вероятностями, сводный балл,
  рекомендация по сделке, доходность вложения, дисконт без оценки), перечислены в
  декомпозиции — и **названы на самих экранах**, чтобы отсутствие не читалось как
  благополучие.
- **Выходы дела — три, состав один** (SPEC, Приложение У): экран, DOCX (`app/audit_docgen.py`)
  и XLSX (`frontend/src/auditExport.ts`), плюс печатный бланк `AuditPrintReport.tsx`
  (число листов **считается**, а не пишется). Порядок разделов — порядок чтения
  инвесткомитетом: вывод и находки, потом числа под ними.
- **Интерфейс.** Дело — страница с разделами (`AuditSubjectPage`, группировка вкладок
  проверяется `AuditSubjectSections.test.ts`: ни одна вкладка не потеряна и принадлежит
  ровно одному разделу). Сравнение дел — `/audit/compare`, онбординг — `/audit/onboarding`
  (заводит настоящее дело одним запросом на последнем шаге). Вход, регистрация и сплеш
  **следуют продукту** (`currentProduct()`): у `/login` своего продукта нет, берётся
  последний выбранный.

## Контракт фронтенда с бэкендом

- `api/schema.d.ts` генерируется из OpenAPI (`npm run gen:api`), свежесть сверяет CI.
  `api/model.ts` — **ручное** зеркало модели проекта, им типизированы вкладки редактора;
  его сверяет `api/model.contract.test.ts` по `backend/openapi.json`: у каждого интерфейса
  есть схема, полей мимо контракта нет, обязательные поля контракта присутствуют.
- **Сверяются имена, не типы.** Зеркало намеренно сужает деньги до `string` (во float-поле
  нельзя положить число) и допускает частично заполненные объекты — требование точного
  совпадения типов заставило бы его ослабнуть. Ловятся переименования и пропажи: без этого
  переименование поля в бэкенде доходило до пользователя молча (редактор пишет старый ключ,
  сервер игнорирует, введённое значение пропадает без ошибки).
- Расхождения имён между слоями — в явной карте `ALIASES` (`CustomTax`→`Tax`,
  `ProjectDetail`→`ProjectOut`): молчаливый пропуск незнакомого имени означал бы, что
  зеркало можно расширять мимо проверки.
