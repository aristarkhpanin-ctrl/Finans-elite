# Финанс-Аудит — декомпозиция реализации (план по этапам)

> План сборки второго продукта платформы по спецификации `FINANS-AUDIT-SPEC.md`. Идём по
> этапам **A → H**; каждый под-шаг — отдельный коммит с проверкой. Разбивка детальная,
> чтобы по ней можно было двигаться последовательно и предсказуемо.

## Принципы (соблюдаются на каждом шаге)

- **Отдельное чистое ядро `backend/audit_core/`** рядом с `calc_core/`; общий фундамент
  (`money`/Decimal, `series`, каталог строк отчётов, `reports/ratios`, ревью) переиспользуется.
- **`calc_core` (первый продукт) и его golden-мастер не затрагиваются** — второй продукт не
  меняет методику первого.
- **Дисциплина точности:** `Decimal`, фиксированный контекст, **свой golden-мастер аудита**,
  инвариант **актив = пассив** (`B20 = B34`) на всех эталонах.
- **Данные раздельны:** новые таблицы с RLS по `org_id` (как `projects`); первый продукт не
  трогается.
- **Тема:** фиолетовый набор токенов; переключение продукта переключает тему. Один набор
  компонентов — без дублирования CSS.
- Каждый под-шаг: реализация → тест (аналитический/unit) → проверка (`pytest` / `tsc` +
  `build` + `vitest`) → коммит.

## Порядок и «срез ценности»

Минимально полезный продукт (MVP) = **A + B + C**: выбрать продукт → ввести отчётность →
получить аналитическую форму, коэффициенты и тренды. Далее D–H наращивают диагностику,
заключение, импорт, методики, консолидацию.

**Цель:** на сайте можно выбрать продукт «Аудит», он открывается в фиолетовой теме с пустым
рабочим пространством; первый продукт работает как раньше.

- [x] **A1. Система тем — второй набор токенов.** Фиолетовый набор токенов в `styles.css`
  (`:root[data-product="audit"]` + тёмный вариант): зелёные токены повёрнуты по оттенку на
  +130° при сохранении S/L (тот же градиент, но фиолетовый); danger/warn не тронуты. Активатор
  `components/product.ts` ставит/снимает `data-product` на `<html>` (с запоминанием выбора для
  общих страниц).
- [x] **A2. Продуктовый переключатель.** Пилюля-переключатель `.prod-switch` в шапке
  (`Layout.tsx`, меню «Финанс-Элит / Финанс-Аудит») + строка продукта в мобильном drawer;
  бренд и навигация в шапке зависят от продукта.
- [x] **A3. Роутинг и заглушка.** Маршрут `/audit` → `AuditHomePage` (пустое состояние
  «раздел в разработке»); навигация продукта — «Субъекты · Организация».
- [x] **A4. Проверка.** `tsc` + `build` + `vitest` (64) зелёные; тема переключается по
  продукту; первый продукт без регрессий.

**Готово** (реализовано): переключатель работает, `/audit` открывается в фиолетовой теме,
первый продукт цел.

## Фаза B. Модель данных и ввод фактической отчётности

**Цель:** субъект анализа с периодами и введёнными балансом/ОПУ; контроль сходимости.

- [x] **B1. Backend-модель (pydantic).** `audit_core`: `AuditSubjectModel` (реквизиты,
  валюта, отрасль, `AuditPeriod` год/квартал, `balance`/`income` по агрегатам РСБУ) +
  каталог строк ввода (`lines.py`) + инвариант `актив = пассив` (`balance_gap`/`is_balanced`).
- [x] **B2. БД + миграция.** Таблица `audit_subjects` (JSON-модель) + миграция
  `b2c4d6e8f0a1` с RLS по `org_id` (как `projects`; на SQLite — no-op).
- [x] **B3. CRUD + API.** CRUD субъектов (create/list/get/update/delete, фильтр по org_id) +
  схемы + роуты `/api/v1/audit/subjects[...]` (права переиспуют проектные). Тесты
  (`test_audit_subjects.py`): CRUD, флаг сходимости, изоляция по организации, авторизация.
- [x] **B4. Frontend — ввод.** Список субъектов (`AuditHomePage`); рабочее пространство
  (`AuditSubjectPage`) — вкладки «Субъект» (реквизиты, периоды) и «Ввод отчётности» (грид
  «статья × период» для баланса-актива/пассива и ОПУ); API-клиент `api/audit.ts`.
- [x] **B5. Контроль сходимости.** Баннер `актив = пассив` по периодам (живой расчёт на
  фронте + флаг `balanced`/`balance_gap` с бэкенда).

**Готово** (реализовано): субъект создаётся/хранится/редактируется, отчётность вводится по
периодам, сходимость показывается, изоляция по организации покрыта тестом. Импорт из Excel — фаза F.

## Фаза C. Аналитическое ядро `audit_core`

**Цель:** из введённой отчётности — аналитическая форма, коэффициенты, тренды.

- [x] **C1. Приведение к аналитической форме.** Введённые агрегаты + производные подытоги
  (оборотные активы, итоги актива/пассива; валовая/операционная прибыль, прибыль до налога,
  чистая прибыль). Инвариант «актив = пассив» — в результате (`balance_gap`/`balanced`).
- [x] **C2. Горизонтальный + вертикальный анализ.** Δ и темп к предыдущему периоду (первый —
  база); доля строки в базе (баланс — суммарный актив, ОПУ — выручка).
- [x] **C3. Коэффициенты.** 4 группы (ликвидность, оборачиваемость, устойчивость,
  рентабельность) на аналитической форме по периодам. Квартальные потоки приводятся к году
  (×4); показатели «в днях» — по длине периода; нулевая база → `None`.
- [x] **C4. `AuditResult` + API.** Датакласс результата + сериализация + роут
  `POST /api/v1/audit/subjects/{id}/analyze` (+ схемы ответа).
- [x] **C5. Golden-мастер аудита.** `tests/golden_audit` на 2 эталонах (годовой и
  квартальный), `UPDATE_AUDIT_GOLDEN=1`; 8 аналитических тестов с ручными числами; проверка
  сходимости эталонов.

**Готово** (реализовано): ввод → анализ → коэффициенты/тренды считаются детерминированно;
golden аудита и инвариант зелёные; UI — вкладки «Отчёты», «Коэффициенты», «Тренды».
**MVP (A+B+C) собран.**

> Отступление от исходного плана (осознанное): движок коэффициентов первого продукта
> (`reports/ratios.py`) **не переиспользуется напрямую** — он требует полного набора
> 4 отчётов (кэш-фло, использование прибыли) и 34-строчного баланса, которых во вводе
> факта нет. Переиспользованы **формулы и соглашения именования**, расчёт — на агрегатах
> аудита. Иначе пришлось бы «досочинять» недостающие строки — это фальшивая точность.

## Фаза D. Диагностика банкротства + нормативы

**Цель:** «светофор» финансового состояния и риска банкротства.

- [x] **D1. Скоринги банкротства.** Модели Альтмана **Z′** (пятифакторная, непубличные) и
  **Z″** (четырёхфакторная, непроизводственные) по учётным величинам, с зонами
  (риск / неопределённость / устойчивость). Memo-строка «нераспределённая прибыль»
  (`M_RETAINED`) — расшифровка капитала, **в итог пассива не входит**; без неё модели с
  этим фактором дают `None` и поясняют причину (не подставляют ноль).
- [x] **D2. Нормативные пороги.** Универсальные пороги (приложение Е) → статус
  `good`/`warn`/`risk` по каждому показателю и периоду.
- [x] **D3. Сводный «светофор».** `ok`/`warning`/`risk` **по последнему периоду** (текущее
  состояние; история — в трендах) + текстовое пояснение с числом сработавших признаков.
- [x] **Тесты:** 10 тестов (формулы по опубликованным коэффициентам, зоны, нормативы,
  светофор по последнему периоду, «нет данных» ≠ ноль); golden аудита перегенерирован
  (дрейф проверен как чисто аддитивный). UI — вкладка «Диагностика».

> **Два осознанных отступления от плана (методика важнее буквы ТЗ):**
> 1. **Классическая пятифакторная модель для публичных компаний не реализована** — её
>    фактор X4 требует **рыночной капитализации**, которой во вводе фактической отчётности
>    нет. Реализованы модификации Альтмана по учётным величинам (Z′/Z″) — они и применимы
>    к непубличным компаниям, составляющим основную аудиторию.
> 2. **Двухфакторная модель исключена.** При проверке выяснилось, что её максимум при любых
>    допустимых входах равен `−0.3877 + 0.0579 ≈ −0.33`, то есть **всегда** ниже границы
>    риска (0): модель структурно не способна подать сигнал и даже для неплатёжеспособного
>    предприятия показала бы «низкий риск». Ложное спокойствие в диагностической панели
>    опаснее отсутствия индикатора. Факт зафиксирован численно в тесте.

## Фаза E. Экспертное заключение и экспорт

**Цель:** связный авто-текст заключения + выгрузка.

- [x] **E1. Авто-текст заключения.** `audit_core/opinion.py` — детерминированный текст без ИИ:
  интро по «светофору» → ключевые показатели последнего периода → динамика (выручка, валюта
  баланса, убыток) → находки (нарушенные нормативы + модели в зоне риска) → вердикт.
  Неопределённые показатели **опускаются**, а не подставляются нулём; несходящийся баланс
  оговаривается отдельно. Поле `opinion` в ответе анализа.
- [x] **E2. Экспорт.** `app/audit_docgen.py` — DOCX (титул → заключение → аналитическая форма →
  коэффициенты по 4 группам → диагностика), реюз помощников `docgen` первого продукта;
  эндпоинт `GET /api/v1/audit/subjects/{id}/report.docx`. UI — вкладка «Заключение» с текстом
  и кнопкой «Скачать DOCX».
- [x] **Тесты:** 8 тестов (структура заключения на здоровом/неустойчивом, оговорка о
  несходящемся балансе, опускание неопределённых показателей, структура DOCX, эндпоинт,
  наличие opinion в ответе анализа).

> XLSX/CSV/PDF-экспорт таблиц аудита — v2: в первом продукте он живёт на клиенте
> (`export.ts`) поверх иной структуры отчётов; для аудита DOCX-документа достаточно,
> чтобы выдать результат заказчику.

## Фаза F. Импорт РСБУ из Excel

**Цель:** загрузка форм 1/2 из файла.

- [x] **F1. Шаблон XLSX** — `frontend/src/auditXlsx.ts`: `buildAuditTemplate` (разделы
  «баланс-актив / баланс-пассив / расшифровка / ОПУ», строки × периоды) + `applyAuditRows`
  (иммутабельное наложение), обёртки `downloadAuditTemplate`/`parseAuditXlsx` (ленивый
  клиентский I/O). Round-trip: формат задаёт приложение — чужую структуру не угадываем.
- [x] **F2. Маппинг** — по **коду** строки (колонка 1), при его отсутствии — по названию
  статьи; отчёт `matched/skipped/ignored`. Периоды и реквизиты субъекта импорт **не меняет**
  (структуру задаёт субъект, файл приносит только числа).
- [x] **Тесты:** 10 unit-тестов (round-trip, матч по коду и по названию, нормализация
  запятой/разрядов/пустых, приведение к числу периодов, служебные строки, неизвестные
  строки, неизменность периодов). UI — кнопки «Шаблон XLSX»/«Импорт XLSX» на вкладке ввода.

> **Попутно закрыт пробел фазы D:** строка «в т.ч. нераспределённая прибыль» (`M_RETAINED`)
> существовала в ядре, но **не была выведена в UI** — то есть пользователь не мог её ввести
> и модели Альтмана всегда показывали бы «не рассчитан». Добавлен грид «Расшифровка
> (в итог пассива не входит)» и строка в шаблоне импорта.

## Фаза G. Пользовательские методики

**Цель:** свои показатели/таблицы/выводы поверх результата.

- [x] **G1. Реюз языка формул платформы** (`calc_core.formula`) над аналитической формой:
  `AuditSubjectModel.user_metrics` (имя + формула) → `AuditResult.user_metrics`. Окружение —
  коды строк аналитической формы (`A_*`/`P_*`/`I_*`/`M_RETAINED`, включая производные подытоги
  `A_TOTAL`/`I_EBIT`/`I_NET`) + `N` (число периодов). Ошибка формулы **не роняет анализ**:
  показатель получает сообщение и нули (как таблицы первого продукта).
- [x] **Тесты:** 5 тестов (формулы над строками и подытогами, доступ к memo и `N`, ошибка
  формулы не ломает остальной анализ, инертность без методик, показатели в API и DOCX).
  Golden аудита перегенерирован — дрейф проверен как чисто аддитивный.
- [x] **UI:** вкладка «Методики» — редактор показателей (имя + формула), подсказка со
  списком доступных кодов, таблица результата по периодам, явная пометка ошибочных формул.
  DOCX — раздел «Пользовательские показатели».

> Отступление: вместо «таблиц» первого продукта (таблица → строки) сделан **плоский список
> показателей** — в аудите методика это набор своих коэффициентов, группировка в таблицы
> избыточна. Язык формул и поведение при ошибке — те же.

## Зависимости и контроль качества

- Порядок обязателен для A→B→C (каркас → данные → анализ). D–H независимы после C и могут
  идти в любом порядке по приоритету.
- На каждом «ядровом» шаге (C–H backend): свой golden аудита + инвариант `актив = пассив`;
  **golden первого продукта проверяется, что не изменился**.
- Frontend: `tsc` + `build` + `vitest` на каждом шаге; первый продукт без регрессий.
- Каждая фаза закрывается обновлением этого файла (чекбоксы) и заметкой в `CLAUDE.md`.
