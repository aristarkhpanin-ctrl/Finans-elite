# Финанс-Аудит — декомпозиция реализации (план по этапам)

> План сборки второго продукта платформы по спецификации `FINANS-AUDIT-SPEC.md`. Идём по
> этапам **A → H**; каждый под-шаг — отдельный коммит с проверкой. Разбивка детальная,
> чтобы по ней можно было двигаться последовательно и предсказуемо.

## Принципы (соблюдаются на каждом шаге)

- **Отдельное чистое ядро `backend/audit_core/`** рядом с `calc_core/`; общий фундамент
  (`money`/Decimal, `series`, каталог строк отчётов, `reports/ratios`, ревью) переиспользуется.
- **`calc_core` (первый продукт) и его golden-мастер не затрагиваются** — второй продукт не
  меняет методику первого.
- **Дисциплина точности:** `Decimal`, фиксированный контекст, **свой golden-мастер аудита**,
  инвариант **актив = пассив** (`B20 = B34`) на всех эталонах.
- **Данные раздельны:** новые таблицы с RLS по `org_id` (как `projects`); первый продукт не
  трогается.
- **Тема:** фиолетовый набор токенов; переключение продукта переключает тему. Один набор
  компонентов — без дублирования CSS.
- Каждый под-шаг: реализация → тест (аналитический/unit) → проверка (`pytest` / `tsc` +
  `build` + `vitest`) → коммит.

## Порядок и «срез ценности»

Минимально полезный продукт (MVP) = **A + B + C**: выбрать продукт → ввести отчётность →
получить аналитическую форму, коэффициенты и тренды. Далее D–H наращивают диагностику,
заключение, импорт, методики, консолидацию.

## Фаза C. Аналитическое ядро `audit_core`

**Цель:** из введённой отчётности — аналитическая форма, коэффициенты, тренды.

- [x] **C1. Приведение к аналитической форме.** Введённые агрегаты + производные подытоги
  (оборотные активы, итоги актива/пассива; валовая/операционная прибыль, прибыль до налога,
  чистая прибыль). Инвариант «актив = пассив» — в результате (`balance_gap`/`balanced`).
- [x] **C2. Горизонтальный + вертикальный анализ.** Δ и темп к предыдущему периоду (первый —
  база); доля строки в базе (баланс — суммарный актив, ОПУ — выручка).
- [x] **C3. Коэффициенты.** 4 группы (ликвидность, оборачиваемость, устойчивость,
  рентабельность) на аналитической форме по периодам. Квартальные потоки приводятся к году
  (×4); показатели «в днях» — по длине периода; нулевая база → `None`.
- [x] **C4. `AuditResult` + API.** Датакласс результата + сериализация + роут
  `POST /api/v1/audit/subjects/{id}/analyze` (+ схемы ответа).
- [x] **C5. Golden-мастер аудита.** `tests/golden_audit` на 2 эталонах (годовой и
  квартальный), `UPDATE_AUDIT_GOLDEN=1`; 8 аналитических тестов с ручными числами; проверка
  сходимости эталонов.

**Готово** (реализовано): ввод → анализ → коэффициенты/тренды считаются детерминированно;
golden аудита и инвариант зелёные; UI — вкладки «Отчёты», «Коэффициенты», «Тренды».
**MVP (A+B+C) собран.**

> Отступление от исходного плана (осознанное): движок коэффициентов первого продукта
> (`reports/ratios.py`) **не переиспользуется напрямую** — он требует полного набора
> 4 отчётов (кэш-фло, использование прибыли) и 34-строчного баланса, которых во вводе
> факта нет. Переиспользованы **формулы и соглашения именования**, расчёт — на агрегатах
> аудита. Иначе пришлось бы «досочинять» недостающие строки — это фальшивая точность.

## Фаза D. Диагностика банкротства + нормативы

**Цель:** «светофор» финансового состояния и риска банкротства.

- [x] **D1. Скоринги банкротства.** Модели Альтмана **Z′** (пятифакторная, непубличные) и
  **Z″** (четырёхфакторная, непроизводственные) по учётным величинам, с зонами
  (риск / неопределённость / устойчивость). Memo-строка «нераспределённая прибыль»
  (`M_RETAINED`) — расшифровка капитала, **в итог пассива не входит**; без неё модели с
  этим фактором дают `None` и поясняют причину (не подставляют ноль).
- [x] **D2. Нормативные пороги.** Универсальные пороги (приложение Е) → статус
  `good`/`warn`/`risk` по каждому показателю и периоду.
- [x] **D3. Сводный «светофор».** `ok`/`warning`/`risk` **по последнему периоду** (текущее
  состояние; история — в трендах) + текстовое пояснение с числом сработавших признаков.
- [x] **Тесты:** 10 тестов (формулы по опубликованным коэффициентам, зоны, нормативы,
  светофор по последнему периоду, «нет данных» ≠ ноль); golden аудита перегенерирован
  (дрейф проверен как чисто аддитивный). UI — вкладка «Диагностика».

> **Два осознанных отступления от плана (методика важнее буквы ТЗ):**
> 1. **Классическая пятифакторная модель для публичных компаний не реализована** — её
>    фактор X4 требует **рыночной капитализации**, которой во вводе фактической отчётности
>    нет. Реализованы модификации Альтмана по учётным величинам (Z′/Z″) — они и применимы
>    к непубличным компаниям, составляющим основную аудиторию.
>    *(Снято в v2: капитализация добавлена как строка-расшифровка, см. ниже.)*
> 2. **Двухфакторная модель исключена.** При проверке выяснилось, что её максимум при любых
>    допустимых входах равен `−0.3877 + 0.0579 ≈ −0.33`, то есть **всегда** ниже границы
>    риска (0): модель структурно не способна подать сигнал и даже для неплатёжеспособного
>    предприятия показала бы «низкий риск». Ложное спокойствие в диагностической панели
>    опаснее отсутствия индикатора. Факт зафиксирован численно в тесте.

**Цель:** связный авто-текст заключения + выгрузка.

- [x] **E1. Авто-текст заключения.** `audit_core/opinion.py` — детерминированный текст без ИИ:

  и кнопкой «Скачать DOCX».
- [x] **Тесты:** 8 тестов (структура заключения на здоровом/неустойчивом, оговорка о
  несходящемся балансе, опускание неопределённых показателей, структура DOCX, эндпоинт,

## Фаза H. Консолидация группы («Интегратор»)

**Цель:** свод отчётности группы предприятий.

- [x] **H1. Свод** — `audit_core/consolidate.py`: `consolidate_subjects(members)` складывает
  строки баланса (включая справочные) и ОПУ **по совпадающим подписям периодов**, затем к
  своду применяется обычный `analyze` (коэффициенты, диагностика, заключение — для группы
  как для одного предприятия). API `POST /api/v1/audit/consolidate`; UI — раздел «Группа».
- [x] **Тесты:** 9 тестов (суммирование, сопоставление по подписи а не позиции, только общие
  периоды, отсутствие общих периодов, оговорка о внутригрупповых оборотах, свод справочной
  строки, пустой список, эндпоинт, изоляция по организации).

> **Два методических решения (заявлены явно, а не умолчаны):**
> 1. **Внутригрупповые обороты не исключаются** — это арифметический свод, а не полная
>    консолидация по правилам учёта. Для исключения взаимных расчётов, взаимной выручки и
>    долей участия нужны данные о внутригрупповых операциях, которых во вводе фактической
>    отчётности нет. Свод **всегда** выводит это предупреждение (и в API, и в UI), чтобы не
>    создавать видимость аудиторской консолидации. Исключение оборотов — v2.
>    *(Снято в v2: величины вводятся пользователем и вычитаются парно, см. ниже. Без них
>    оговорка остаётся прежней.)*
> 2. **Период входит в свод, только если он есть у всех участников** (сопоставление по
>    подписи, не по порядковому номеру). Иначе сумма занижала бы группу по этому периоду.
>    Пропущенные периоды перечисляются в предупреждении.

> Реюз `consolidate_detailed` первого продукта не подошёл: он консолидирует **прогнозные
> модели проектов** (сложение помесячных рядов ProjectModel), а здесь складывается
> фактическая отчётность по отчётным периодам — иные сущности и правила сопоставления.

## Зависимости и контроль качества

- Порядок обязателен для A→B→C (каркас → данные → анализ). D–H независимы после C и могут
  идти в любом порядке по приоритету.
- На каждом «ядровом» шаге (C–H backend): свой golden аудита + инвариант `актив = пассив`;
  **golden первого продукта проверяется, что не изменился**.
- Frontend: `tsc` + `build` + `vitest` на каждом шаге; первый продукт без регрессий.
- Каждая фаза закрывается обновлением этого файла (чекбоксы) и заметкой в `CLAUDE.md`.

**Статус: все фазы A–H реализованы.** Продукт «Финанс-Аудит» закрыт по плану: тема и
переключатель · ввод отчётности · аналитика · диагностика · заключение и DOCX · импорт из
Excel · пользовательские методики · консолидация группы.

## v2 — реализовано

- [x] **Свои нормативы показателей.** `AuditSubjectModel.thresholds` — норматив
  (`ratio`, `direction`, `risk_edge`, `good_edge`) переопределяет универсальный порог
  диагностики; можно задать порог и показателю, у которого универсального нет.
  **Несогласованный порог** (границы противоречат направлению) не применяется молча —
  остаётся универсальный + предупреждение. Отраслевые справочники так и не «выдумываются»:
  норматив задаёт пользователь под свою методику. UI — редактор на вкладке «Методики».
- [x] **Исключение внутригрупповых оборотов.** `Elimination(receivables, revenue)` в
  консолидации: взаимная задолженность вычитается **парно** (дебиторка + кредиторка),
  взаимная выручка — **парно** с себестоимостью, поэтому равенство «актив = пассив»
  сохраняется (проверено тестом). Сумма сверх свода **обрезается** с предупреждением —
  вычесть больше, чем есть, значит получить отрицательную статью. Текст оговорки меняется:
  без исключений — о завышении, с исключениями — что именно вычтено. UI — тумблер и поля
  на странице «Группа». *(Дополнено ниже: доли участия и нереализованная прибыль.)*
- [x] **Помесячная периодичность.** `AuditPeriod.kind` принимает `month` наравне с
  `year`/`quarter`. В `analysis.py` вместо двух карт (`_DAYS`, `_YEAR`) — одна
  `_PERIOD: kind → (длина в днях, множитель приведения к году)`, и множитель задан
  **явно** (1 / 4 / 12), а не выведен делением `365/длина`: месячный показатель равен
  годовому ровно в 12 раз (проверено точным равенством `Decimal`, без «почти»).
  Показатели «в днях» считаются по длине месяца `365/12`; структурные показатели (доли,
  маржа) от периодичности не зависят. Ядро расчётов первого продукта не затронуто.
- [x] **XLSX-выгрузка таблиц аудита.** `frontend/src/auditExport.ts` — книга по листу на
  раздел: аналитическая форма · тренды · структура · коэффициенты · диагностика ·
  методики · заключение. Собирается **из готового ответа `/analyze`** (ничего не
  пересчитывается → файл не может разойтись с экраном), числа выгружаются числами с
  форматом (деньги / проценты / коэффициенты). Ключевое соглашение аналитики держится и
  в файле: **неопределённый показатель — пустая ячейка, а не ноль** (ноль в Excel читался
  бы как посчитанное значение). Пустые разделы листов не создают; пустой анализ выгрузки
  не даёт. UI — кнопка «Выгрузка XLSX» на аналитических вкладках субъекта и на своде
  группы (`AuditAnalysis` там той же формы → выгрузка переиспользуется целиком).

- [x] **Сохранённые группы предприятий.** Таблица `audit_groups` (миграция `c3d5e7f9a1b2`,
  RLS как у `audit_subjects`) + CRUD и API `/api/v1/audit/groups[/{id}]`, свод —
  `POST …/groups/{id}/analyze`. Группа хранит **состав, а не результат**: участники
  (`subject_id`) и внутригрупповые обороты; числа всегда пересчитываются по текущей
  отчётности участников, поэтому «сохранённый свод» не может устареть.
  Решения по честности:
  - **Удалённый участник не исчезает молча.** Свод считается по оставшимся, а выбывшие
    названы **первой** оговоркой и отдельным полем `missing_members`: состав изменился —
    значит, показатели группы уже не те, что были при сохранении.
  - **Имя участника хранится как «надгробие».** У живого участника имя берётся из самого
    субъекта (переименование видно в своде), сохранённое имя нужно только чтобы назвать
    того, кого удалили, — иначе от него остался бы голый идентификатор.
  - **Группа без живых участников — пустой свод с оговоркой, а не ошибка.** Группа
    существует, в ней просто некого сводить (`consolidate_subjects` на пустом списке
    по-прежнему бросает `ValueError` — пустой случай разбирается слоем API).
  - **Субъект другой организации считается выбывшим**, а не подмешивается в свод
    (изоляция арендатора: он попросту не находится).
  - UI — блок «Сохранённые группы» на странице «Группа»: открыть (состав в форму + свод),
    сохранить/обновить состав, удалить. Выбывшие участники показаны отдельным
    предупреждением с кнопкой «убрать из состава». Сохранённая группа без правок сводится
    своим эндпоинтом (он знает про выбывших), правленая форма — разовым сводом по живым.
- [x] **Тесты:** 9 (CRUD и состав, свод = сумма участников, пересчёт после правки

- [x] **Классическая модель Альтмана (публичные компании).** Рыночная капитализация
  введена как строка-расшифровка `M_MARKET_CAP` (реюз машинерии memo-строк: ввод, XLSX,
  формулы методик; в итоги баланса не входит). Классическая модель 1968 года —
  `1.2·X1 + 1.4·X2 + 3.3·X3 + 0.6·X4 + 1.0·X5`, где **X4 = рыночная капитализация /
  учётные обязательства**; зоны < 1,81 / 1,81–2,99 / > 2,99. Решения:
  - **Модель показывается, только если капитализация введена.** Это отличается от
    нераспределённой прибыли: та есть у любого предприятия и может быть просто не внесена
    (модель выводится «не рассчитанной»), а капитализации у непубличной компании **не
    существует** — строка «не рассчитано» намекала бы на пробел во вводе там, где модель
    неприменима в принципе.
  - **Балансовый капитал вместо рыночного не подставляется.** Такая подмена даёт Z′, но под
    именем классической модели — тест `test_public_model_uses_market_not_book_equity`
    фиксирует, что фактор действительно рыночный.
  - **Введённый ноль — значение, а не «не введено»** (капитал обесценен): модель считается
    с X4 = 0, а итоговую зону определяет она сама, а не наша поправка.
  - **При консолидации капитализация не складывается** (`MEMO_SUM_CODES`): капитализация
    материнской компании уже включает стоимость дочерних, и сумма по группе была бы двойным
    счётом. Строка в свод не переносится, классическая модель для группы не считается, о
    чём выводится оговорка — вместо правдоподобного, но ложного числа.
- [x] **Тесты:** 8 (формула и зона, рыночный фактор ≠ балансовый, отсутствие модели без
  капитализации, введённый ноль, общий фактор накопленной прибыли, влияние на «светофор»,
  несуммирование при своде и тишина без капитализации).

- [x] **Доли участия и нереализованная прибыль в запасах.** `Elimination` дополнена полями
  `investments` и `unrealized_profit`; таблица пар (что из чего вычитается) — в докстринге
  `_eliminate`:

  | Что исключаем | Актив | Пассив / ОПУ |
  |---|---|---|
  | Взаимная задолженность | `A_RECEIVABLE` | `P_SHORT` |
  | Взаимная выручка | `I_REVENUE` | `I_COGS` |
  | Вложения в капитал (доли участия) | `A_FIXED` | `P_EQUITY` |
  | Нереализованная прибыль в запасах | `A_INVENTORY` | `P_EQUITY` (+ `I_COGS`) |

  Решения:
  - **Нереализованная прибыль снимается и в балансе, и в ОПУ.** Уменьшение запасов и
    капитала — балансовая сторона; восстановление себестоимости — та же операция глазами
    отчёта о финансовых результатах. Без второй половины отчёты рассказывали бы разные
    истории об одной сделке. Справочная `M_RETAINED` уменьшается на ту же сумму, иначе
    фактор моделей Альтмана противоречил бы капиталу, из которого прибыль уже вычтена.
  - **Обрезка последовательная:** нереализованная прибыль ограничивается капиталом,
    **уже уменьшенным** на вложения, — иначе суммарное вычитание могло бы увести капитал
    в минус.
  - **Гудвилл и неконтролирующая доля не выделяются** — статей под них в аналитической
    форме нет, а «досочинять» строки баланса нельзя. Вычитается ровно вложение по
    балансовой стоимости, и оговорка прямо говорит: при доле участия менее 100% капитал
    группы показан по стоимости вложения, а не по чистым активам дочерних компаний.
  - **Оговорка перечисляет ровно то, что вычтено** (а не общий список видов): если
    исключена только задолженность, о выручке в тексте не говорится.
- [x] **Попутно исправлено: справочные строки в своде.** Строка `M_RETAINED` переносилась
  в свод всегда, даже когда её никто из участников не вводил, — и превращалась в ноль.
  Диагностика группы считала модели Альтмана с накопленной прибылью 0 там, где по тем же
  субъектам поодиночке они честно оставались нерассчитанными. Теперь memo-строка попадает
  в свод, **только если её кто-то ввёл** (тест `test_memo_row_absent_when_nobody_entered_it`).
