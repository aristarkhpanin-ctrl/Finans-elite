# Доходы участников — план реализации (U0–U2)

> Пакет №7 gap-анализа (`GAP-ANALYSIS-PE.md` §4.3): денежные потоки каждого участника
> финансирования (акционеры, кредиторы) и индивидуальные NPV/IRR — «эффективность
> участия», частый запрос банков (IRR собственного капитала). Новый раздел результата,
> старые строки отчётов не меняются.

## 0. Зафиксированные решения (Q1–Q6)

- **Q1. Участники v1:** «Акционеры» (совокупно) + каждый заём (`financing.loans`)
  отдельным участником-кредитором. Кредитная линия автоподбора, лизингодатели,
  привилегированные акционеры — v2.
- **Q2. Поток акционеров** = −C21 (взносы) + C26 (дивиденды) помесячно. Метрики в двух
  видах: **без терминальной стоимости** и **с терминальной стоимостью** — условным
  изъятием собственного капитала на конец горизонта (B33 последнего месяца, «чистые
  активы», согласовано с `valuation.net_assets`). Оба честны: без TV — «живые деньги»,
  с TV — классический equity-IRR для банка.
- **Q3. Поток кредитора** (по займу) = −выдача + погашение тела + проценты, из того же
  графика, что строит движок (`_loan_schedule`); валютные займы пересчитываются в рубли
  по `FX[t]` (как в конвейере) — рублёвая доходность кредитора включает курсовой эффект.
  Проценты «на прибыль» (I24) — тоже доход кредитора (без разницы для его потока).
  **Терминальная стоимость кредитора** — остаток непогашенного тела на конец горизонта
  (по `FX` последнего месяца): без неё IRR займа, чей график выходит за горизонт,
  бессмысленно занижена (демо: последний платёж тела в месяце n — за горизонтом).
  Как и у акционеров — оба варианта метрик (без TV и с TV).
- **Q4. Метрики участника:** NPV по ставке дисконтирования проекта (месячная, как для
  проекта) и годовая IRR потока участника (None, если не определяется). Суммарно:
  вложено (Σ отрицательных), получено (Σ положительных).
- **Q5. Выход** — `CalcResult.participants: list[ParticipantFlow]` (модуль
  `calc_core/engine/participants.py`, читает модель + готовые отчёты). Пустое
  финансирование (нет ни взносов, ни дивидендов, ни займов) → пустой список.
  **В golden-снимок — при непустом списке** (как budget/product_margins): аналитика с
  числами, фиксируем. `ENGINE_VERSION → 0.9.29`; дифф golden = версия + новые блоки
  `participants` в кейсах с финансированием (старые числа не меняются — ревью диффа).
- **Q6. Отображение:** карточка-таблица «Доходы участников» на сводке результатов
  (участник, вложено, получено, NPV, IRR; для акционеров — обе строки: без TV и с TV)
  + такая же таблица в DOCX-бизнес-плане (после показателей эффективности).

## 1. Архитектура

```
calc_core/reports/result.py          # ParticipantFlow (dataclass) + CalcResult.participants
calc_core/engine/participants.py     # compute_participants(model, cashflow, balance, n)
calc_core/serialize.py               # participants → снимок (при непустом)
app/schemas.py                       # ParticipantOut в CalcResponse
app/docgen.py                        # таблица «Доходы участников»
frontend: SummaryView / ProjectResultsPage  # карточка на сводке
```

## 2. Фазы

- [x] **U0.** Ядро: `ParticipantFlow` + `compute_participants` + сериализация +
  `0.9.29` + перегенерация golden (ревью диффа: только новые блоки). Тесты:
  акционерный поток/TV, IRR кредитора ≈ ставке займа (рублёвый заём, равное тело),
  валютный заём (курсовой доход), Σ потоков сходится со строками C21/C26/C22–C24,
  инертность пустого финансирования.
- [ ] **U1.** API + UI + DOCX: `participants` в `CalcResponse`, openapi/`gen:api`,
  карточка на сводке результатов, таблица в docgen; vitest.
- [ ] **U2.** Документация: SPEC (§17, подраздел «Доходы участников»), ROADMAP,
  GAP-ANALYSIS (4.3), CLAUDE.md, этот чеклист.

## 3. Инварианты

- Поток акционеров восстанавливается из отчётов: `flow = C26 − C21` (+ B33 в последнем
  месяце для варианта с TV); Σ потоков кредиторов по займам = C23 + C24 − C22
  (без автолинии). Отчёты не меняются — только новый раздел результата.
