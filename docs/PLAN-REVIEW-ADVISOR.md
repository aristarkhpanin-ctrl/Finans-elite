# Ревью бизнес-плана («линтер модели») — оценка осуществимости и план

> **Статус:** гипотеза / проектные заметки (не в разработке).
> **Суть идеи (заказчик):** после расчёта модель проходит этап «ревью итогового
> бизнес-плана»: система выдаёт рекомендации, подсвечивает узкие места и потенциальные
> риски, а также расхождение «план ↔ вероятное будущее». Пример: если статья издержек
> необоснованно велика для одного продукта, а по остальным реалистична — превью должно
> на это указать.
> **Ключевая гипотеза:** это выполнимо **без ИИ**, на детерминированных правилах
> (утилитах/плагинах), дающих схожий результат.
> **Позиционирование:** такого этапа нет в Project Expert — это наша **первая фича вне
> паритета** с конкурентом.

---

## 0. Вердикт по осуществимости (кратко)

**Осуществимо и без ИИ — да, для большей части задуманного.** По сути это «линтер
финансовой модели»: набор детерминированных правил поверх уже посчитанных отчётов,
показателей, коэффициентов и стохастики (Монте-Карло/чувствительность). Для финансового
продукта правила **предпочтительнее ИИ**: объяснимы, воспроизводимы, не галлюцинируют,
каждое срабатывание можно доказать числом. ИИ later может добавить *формулировку* резюме
человеческим языком — но ядро ценности рулевое.

**Но с тремя оговорками, где я спорю с постановкой (см. §4):**
1. Именно ваш пример — «издержка слишком велика для *одного продукта*» — **сейчас не
   считается**: в модели издержки не привязаны к продукту (`DirectCostLine`/`FixedCostLine`
   не имеют `product_id`; `SalesLine` — имеет). Нужна либо доработка модели (спецификация
   «издержка → продукт»), либо аллокация по доле выручки (допущение, слабый сигнал).
2. «Необоснованно / слишком высоко» в **абсолюте** невыводимо изнутри модели — нужен
   внешний бенчмарк (отраслевые нормы). Изнутри честно детектируются только
   **внутренние несогласованности** и **выбросы** (относительно других статей самой модели).
3. Часть задуманного (реализм траектории роста) — **слишком косвенно** без бенчмарка;
   предлагаю не делать в v1 или показывать как info, а не как риск.

Дальше — что именно доступно движку, каталог правил, архитектура и фазы.

## 1. На каких данных работают правила (что уже есть)

Движок (`calc_core`) после `run(model)` даёт богатый **структурированный** вход для правил:

| Источник | Что даёт правилам |
|---|---|
| **4 отчёта** (I/C/B/P), помесячно | I1 выручка, I5 материалы, I28 чистая прибыль; C29 сальдо денег; B1 касса, B8 оборотные активы, B25 краткосрочные обяз., B20=B34 инвариант, B33 капитал |
| **Показатели** `metrics` | `npv`, `irr_annual`, `pi`, `pb_months`, `dpb_months`, `pv_investments`, `peak_financing_need` |
| **Коэффициенты** (5 групп) | ликвидность («Коэффициент текущей/срочной ликвидности»), оборачиваемость (дни), структура капитала, рентабельность (ROA/ROE), «на акцию» |
| **Безубыточность** | `break_even_revenue`, `margin_of_safety` по месяцам |
| **Оценка бизнеса** | чистые активы, Гордон, DDM, мультипликатор, ликвидационная |
| **Монте-Карло** (уже с риск-метриками) | `probability_npv_positive`, `npv_p5` (VaR95), `npv_cvar_5` (ES95), `npv_sem`, σ, гистограмма |
| **Чувствительность** | `points[]` — NPV/IRR при коэффициентах параметра |
| **Модель (вход)** | помесячные `SalesLine` **по продуктам** (объём×цена), `DirectCostLine`/`FixedCostLine` (по статьям, **не** по продуктам), ставки/налоги/инфляция, финансирование |

**Важное ограничение данных (грунт под §4.1):** выручка есть **по продуктам**
(`SalesLine.product_id`), а издержки — **по статьям, без привязки к продукту**. Значит
per-product **маржа** сейчас непосчитаема.

## 2. Модель результата: `Finding`

Каждое правило возвращает 0..N находок единого вида (как у линтера кода):

```
Finding:
  id: str            # стабильный код правила, напр. "liquidity.cash_gap"
  category: str      # viability | liquidity | structure | assumptions | divergence
  severity: str      # info | warning | risk
  confidence: str    # high | medium | low  (low → показываем как info)
  title: str         # «Кассовый разрыв в мес. 7»
  detail: str        # объяснение с числами
  evidence: {...}    # период(ы), коды строк, значения, ссылки на статьи модели
  recommendation: str# что проверить/сделать
```

Принципы (§4.4): находки — **совет, а не вердикт**; каждая доказана числом (`evidence`);
пороги консервативны и конфигурируемы; худшая severity формирует «светофор» резюме.

## 3. Каталог правил (по группам, с честной оценкой)

Пометки: **[v1]** делаем сразу (прямой, доказуемый сигнал); **[поздн.]** отложить;
**[спорно]** — см. §4.

### A. Жизнеспособность (viability) — прямые, high — **[v1]**
- `viability.npv_negative` — NPV < 0 при заданной ставке → проект разрушает стоимость.
- `viability.irr_below_hurdle` — `irr_annual` < `discount_rate_annual` → не бьёт барьер.
- `viability.pi_below_one` — PI < 1.
- `viability.no_payback` — `pb_months` = None или > горизонта.
- `viability.irr_unreliable` — нестандартный поток (несколько смен знака чистого
  денежного потока) → IRR неоднозначна, показываем с оговоркой (info).

### B. Ликвидность / платёжеспособность (liquidity) — прямые — **[v1]**
- `liquidity.cash_gap` — B1/C29 < 0 в каком-то месяце при **выключенном** автоподборе →
  кассовый разрыв. Evidence: месяц, глубина.
- `liquidity.financing_dependency` — `peak_financing_need` велик относительно
  акционерного капитала (напр. > k·капитал) → сильная зависимость от привлечения.
- `liquidity.current_ratio_low` — «Коэффициент текущей ликвидности» < порога в периодах.
- `liquidity.overleverage` — структура капитала (долг/собств.) выше порога.
- `liquidity.interest_coverage_low` — покрытие процентов низкое (EBIT/проценты из I-кодов).

### C. Структура / реализм (structure) — частично — **[v1 частично]**
- `structure.revenue_concentration` **[v1]** — один продукт > X% суммарной выручки →
  зависимость от одного источника. *Считается* (выручка по продуктам из модели).
- `structure.cost_line_outlier` **[v1, medium]** — одна статья издержек непропорционально
  велика относительно других статей и/или выручки (напр. > медиана·k или вне межквартиля)
  → «проверьте статью». *Считается* на уровне **статьи** (не продукта).
- `structure.negative_margin` **[v1]** — суммарная валовая/операционная маржа отрицательная
  или крайне тонкая → структурная проблема юнит-экономики. *Считается* (агрегатные I-коды).
- `structure.per_product_margin` **[поздн., спорно]** — «маржа продукта X ниже остальных».
  **Заблокировано данными** (издержки не привязаны к продукту). См. §4.1.

### D. Допущения (assumptions) — прямые, но осторожно — **[v1 как warning/info]**
- `assumptions.zero_tax` — ставка налога 0 без явной льготы → проверить.
- `assumptions.discount_below_inflation` — ставка дисконта ниже инфляции → NPV завышен.
- `assumptions.instant_settlement` — все условия оплаты мгновенные (нет дебиторки/
  кредиторки) → оптимистичная касса.
- `assumptions.no_working_capital` / `assumptions.flat_prices` — по вкусу, info.

### E. Траектория (trajectory) — **[спорно, отложить/info]**
- `trajectory.revenue_growth_aggressive` — MoM-рост выручки > X% → агрессивно.
- `trajectory.margin_drift` — маржа улучшается со временем без драйвера.
- **Почему спорно:** «агрессивно/нереалистично» требует бенчмарка; иначе это произвольный
  порог → ложные срабатывания → подрыв доверия. В v1 не делать или только info (§4.3).

### F. Дивергенция «план ↔ вероятное будущее» (divergence) — **сильный сигнал** — **[v1]**
Это и есть прямой ответ на «расхождение плана и возможного будущего», и он **переиспользует
уже готовые** Монте-Карло и чувствительность — ничего нового прогнозировать не нужно.
- `divergence.fragile_positive_npv` — детерминированный NPV > 0, но
  `probability_npv_positive` низкая (напр. < 0.6) → план оптимистичен относительно
  вероятных исходов. Evidence: NPV, P(NPV>0), P5/VaR.
- `divergence.heavy_downside` — `npv_cvar_5` (среднее худших 5%) сильно отрицательный →
  тяжёлый левый хвост.
- `divergence.sensitivity_sign_flip` — NPV меняет знак при ±X% ключевого параметра
  (цена/объём/издержки) из `sensitivity` → хрупкость к конкретному допущению.
- `divergence.wide_dispersion` — σ/|mean| велик → высокая неопределённость оценки.
- Требует, чтобы MC/чувствительность были посчитаны. Advisor может запускать их **сам**
  с дефолтными распределениями (±10–20% по ключевым параметрам) — детерминированно по seed.

**Вывод по каталогу:** A, B, F + `revenue_concentration`/`negative_margin`/`cost_line_outlier`
— уже сейчас дают содержательное, доказуемое ревью. Именно F — «изюм» под задачу
«план ↔ будущее».

## 4. Где я спорю (шероховатости, которые нужно учесть)

### 4.1. Ваш пример (издержка на 1 продукт) блокирован моделью данных
Издержки в модели — по **статьям**, без `product_id`. Поэтому per-product маржу нельзя
получить честно. Варианты:
- **(a) Расширить модель:** привязать `DirectCostLine` к продукту (по сути мини-BOM:
  «на продукт X — столько материалов/сдельной ЗП»). Даёт настоящую юнит-экономику и
  сильные проверки, но это доработка ядра + миграция входных данных.
- **(b) Аллокация издержек по доле выручки/объёма** продукта. Считается сразу, но это
  **допущение**, а не факт → сигнал слабый и может вводить в заблуждение. Годится максимум
  как info с явной оговоркой «оценка при пропорциональном разнесении».
- **Рекомендация:** в v1 не обещать per-product маржу. Сделать сильные проверки, которые
  *считаются* (концентрация выручки, выброс статьи, суммарная маржа). Per-product margin —
  отдельным решением после (a).

### 4.2. «Необоснованно / слишком высоко» — только относительно, не в абсолюте
Движок знает числа, а не отраслевую реальность. Изнутри честно детектируются:
- **внутренние несогласованности** (издержка > выручки, маржа отрицательная, инвариант);
- **выбросы** (статья вне межквартильного размаха относительно других статей плана).
Абсолютное «дорого для этой отрасли» требует **бенчмарка** (набор отраслевых норм). Это не
ИИ, а *данные*: отдельный источник (свой датасет / ввод пользователя «ожидаемые нормы»).
- **Рекомендация:** v1 — только относительные проверки. Бенчмарки — опциональная фаза
  позже (и всё ещё без ИИ).

### 4.3. Пороги — самая тонкая часть; риск «линтера, который врёт»
У каждого правила есть порог (какая ликвидность «низкая»? какой рост «агрессивный»?).
Плохие пороги → ложные срабатывания → пользователь перестаёт верить превью.
- **Рекомендация:** пороги — консервативные, **конфигурируемые** (глобально, позже per-org),
  каждое срабатывание объяснимо числом; уровни severity (info/warning/risk); косвенные
  правила (E) — только info или выключены. Лучше меньше находок, но все — по делу.

### 4.4. Формулировка: советник, а не приговор
Финансовый продукт, выносящий «ваш план плохой» по порогу, опасен. Находки — «места,
которые стоит перепроверить», с доказательством и рекомендацией. «Светофор» резюме — по
худшей severity, но с оговоркой, что это не гарантия и не отказ.

### 4.5. ИИ не нужен для ядра (и это плюс)
Всё вышеперечисленное — детерминированные правила. ИИ мог бы позже **переформулировать**
находки связным текстом-резюме, но: (1) это не обязательно, (2) для финпродукта объяснимость
и воспроизводимость важнее «красивого текста», (3) golden-тесты правил невозможны с ИИ.
Рекомендация: ядро — правила; ИИ — опционально и только как «обёртка формулировки».

## 5. Архитектура реализации

### Backend — чистый детерминированный модуль (в духе ядра)
```
calc_core/review/
  types.py     # Finding, Severity, категории
  rules/       # по одной функции на правило: (ctx) -> list[Finding]
  runner.py    # реестр правил, прогон, агрегация, «светофор»
  config.py    # пороги (значения по умолчанию)
```
- Вход правила `ctx`: `CalcResult` + `ProjectModel` (+ опц. `MonteCarloResult`,
  `SensitivityResult`). Всё уже есть.
- **Детерминизм + golden-тесты:** под каждый rule — крафтовая модель и ожидаемые находки
  (ровно как `test_golden`/аналитические тесты). Это ложится в культуру точности проекта.
- Никаких сторонних «плагинов» не нужно — это внутренний модуль движка. (Плагинность —
  если захотим сторонние наборы правил позже; в v1 избыточно.)

### API
- `POST /api/v1/projects/{id}/review` → считает `run(model)` (+ при необходимости MC с
  дефолтными распределениями и чувствительность по ключевым параметрам) → правила →
  `{ summary: {severity_light, counts}, findings: [...] }`.
- Тяжёлые прогоны (MC) — уже умеем в фоне (Celery): ревью может быть async-задачей.

### Frontend — вкладка «Ревью» на странице результатов
- Баннер-резюме (светофор + «N рисков / M предупреждений / K заметок»).
- Список находок, сгруппированный по severity; каждая — заголовок, объяснение с числами,
  `evidence` со ссылкой на нужный отчёт/период/статью, рекомендация.
- Переиспользует дизайн-систему (карточки/`error-state`/бейджи severity).

## 6. Фазы

- **MVP (v1):** модуль `review` + правила A, B, F + `revenue_concentration`,
  `negative_margin`, `cost_line_outlier`; API-эндпоинт; вкладка «Ревью»; golden-тесты.
  Уже даёт содержательное, доказуемое ревью и прямой сигнал «план ↔ будущее» (F).
- **v2:** доработка модели «издержка → продукт» (BOM) → настоящая per-product юнит-экономика
  и `structure.per_product_margin`; расширение проверок допущений.
- **v3 (опц., без ИИ):** бенчмарки отраслевых норм (свой датасет / ввод пользователя) для
  абсолютных проверок «дорого/дёшево»; конфигурация порогов per-org.
- **v4 (опц.):** ИИ-обёртка — связное текстовое резюме поверх найденных фактов.

## 7. Решения, которые нужны от заказчика
1. Per-product маржа: идём в доработку модели (BOM, вариант 4.1a) или пока отказываемся?
2. Бенчмарки «дорого/дёшево»: нужен ли внешний источник норм, и чей (свой датасет vs ввод
   пользователем)? Или v1 — только относительные проверки?
3. Набор и пороги правил v1: с какого светофора считаем «риск», а не «предупреждение».
4. Где живёт ревью: отдельная вкладка результатов и/или обязательный «шлюз» перед
   финализацией плана?
