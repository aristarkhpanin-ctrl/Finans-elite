# Gap-анализ: Project Expert 7.21 vs Finans-Elite

> Что есть в PE и отсутствует (или реализовано частично) у нас. Основа для планирования
> дальнейшей работы. Источник карты функционала PE — `RESEARCH-ProjectExpert.md` §4–8;
> состояние нашего продукта сверено с кодом (`calc_core`, `app`, `frontend`) на момент
> `engine_version 0.9.19`.
>
> Оценки: **S** — малый шаг (1 фаза), **M** — средний (2–4 фазы), **L** — крупная фича
> (отдельная декомпозиция, как ревью/календарный план). Приоритет: 🔴 ядро паритета,
> 🟡 желательно, ⚪ низкий/спорный.

## Сводка: что уже в паритете (для контекста)

Помесячное ядро на Decimal, 4 отчёта + инвариант B20=B34; налоги (прибыль с переносом
убытков и льготой, имущество, НДС по отгрузке/оплате + импортный, налог с продаж, взносы
с ФОТ); инфляция по 4 группам; две валюты с переоценкой (I25) по всем основным статьям;
запасы (средняя/ФИФО), НЗП, авансы/дебиторка/кредиторка; активы (амортизация, продажа,
переоценка, группы ОС); займы (+валютные, автоподбор кредита), лизинг (операционный,
финансовый, страхование, выкуп), депозиты; детальный стартовый баланс (~20 статей);
календарный план (этапы, связи, иерархия, ресурсы, смета, Гантт); NPV/IRR/PI/PB/DPB,
потребность в капитале; 5 групп коэффициентов; безубыточность; чувствительность,
Монте-Карло (богаче PE: VaR/CVaR/гистограмма), What-If, Integrator/холдинги; оценка
бизнеса (5 методов); актуализация Кэш-фло (план-факт); сверх PE — ревью плана с гейтом
финализации. Платформа: SaaS, RBAC, биллинг ЮKassa, RLS, Celery, PDF/XLSX/CSV.

## 1. Расчётное ядро и методика

### 1.1 ✅ Разнесение издержек по продуктам (рецептура / BOM) — сделано (0.9.20–0.9.21)
**PE:** план производства продукта = материалы (нормы расхода на единицу), сдельная
зарплата, другие издержки — себестоимость и маржа **по каждому продукту**.
**У нас:** `DirectCostLine`/`FixedCostLine` глобальные (без `product_id`); маржа только
суммарная. Это же блокирует пер-продуктные правила ревью (зафиксировано в
`PLAN-REVIEW-ADVISOR.md` как v2) и «привязку издержек к продуктам».
**Сделано** (пакет №1, `PRODUCT-ECONOMICS-DECOMPOSITION.md`): рецептура `Product.bom` +
`piece_wage_per_unit`, справочник материалов; синтетические прямые издержки; маржа по
продуктам (`product_margins`); пер-продуктные правила ревью; UI (рецептура + таблица маржи).

### 1.2 ✅ Произвольные «другие поступления / выплаты» — сделано (0.9.22)
**PE:** отдельные списки прочих доходов/расходов (не связанных с основной деятельностью).
**У нас:** строки `C10`/`C11`, `I20`/`I21` заполняются только машинерией (активы, лизинг,
этапы) — пользовательских статей нет.
**Работа:** списки `OtherIncome`/`OtherExpense` (сумма, месяц/ряд, вкл. в налоговую базу
или нет) → `I20`/`I21` + `C10`/`C11`. Мелкий, но частый запрос.

### 1.3 ✅ MIRR и ARR — сделано (0.9.23)
**PE:** полный набор показателей: PB, DPB, ARR, NPV, PI, IRR, **MIRR**.
**У нас:** нет MIRR (модифицированная IRR с нормой реинвестиций) и ARR (средняя норма
рентабельности).
**Работа:** две функции в `calc_core/metrics.py` + поля в `InvestmentMetrics` + UI-карточки.
Настройка: ставка реинвестиций (по умолчанию = ставке дисконтирования).

### 1.4 🟡 S — Ставка дисконтирования по каждой валюте
**PE:** своя ставка для основной и второй валюты (показатели считаются в обеих валютах).
**У нас:** одна `discount_rate_annual`; показатели только в основной валюте.
**Работа:** `discount_rate_annual_foreign` + пересчёт потока во вторую валюту по FX и
дубль-блок метрик. Спорно по ценности — решить при сверке с эталоном.

### 1.5 ✅ M — Шаг дисконтирования и агрегация отчётов (квартал/полугодие/год)
**PE:** шаг дисконтирования месяц/квартал/полугодие/год; отчёты отображаются агрегированно
(классика PE: первые 2 года по месяцам, дальше по годам).
**У нас:** всё строго помесячно (ядро — правильно), но **отображение** длинных горизонтов
(120–600 мес.) в таблицах нечитабельно.
**Сделано** (пакет №6, `AGGREGATION-DRILLDOWN-DECOMPOSITION.md`): свёртка на уровне
представления — `frontend/src/aggregate.ts` (потоки — суммы, балансы — конец периода,
C28/P2 — начало, P3 = P2 + ΣP1), переключатель «Месяц | Квартал | Год» на отчётах
результатов (дефолт по горизонту); в DOCX — годовая свёртка (пакет №5). Ядро помесячно.
Шаг дисконтирования не менялся (месяц) — отдельная тема при сверке с эталоном.

### 1.6 🟡 S — Дополнительные инвестиции в актив (доинвестирование)
**PE:** к существующему активу добавляются инвестиции (модернизация), меняющие стоимость
и амортизацию.
**У нас:** только новый `Asset`.
**Работа:** либо поле `additional_investments: [(month, amount)]` у `Asset` с пересчётом
амортизации от остаточного срока, либо документированный паттерн «второй актив».

### 1.7 🟡 S — Продажа/выбытие части стартовых ОС
**PE:** стартовый баланс содержит детальные активы, которые можно продавать.
**У нас:** стартовые ОС — один агрегат `fixed_assets_net` (продажа не моделируется);
продажа только плановых `Asset`.
**Работа:** опциональная детализация стартовых ОС списком `Asset` с
`purchase_month = -1`/исторической стоимостью (или документированный обход).

### 1.8 ⚪ S — НМА и незавершённые инвестиции в стартовом балансе
**PE:** отдельные статьи: нематериальные активы, незавершённые инвестиции.
**У нас:** «Другие активы» `B16` не заполняется со старта; НМА как класс с амортизацией
отсутствует.
**Работа:** статьи стартового баланса → `B16` (по образцу 0.9.10–0.9.12); НМА как
категория актива (амортизация есть — только новая категория разноски).

### 1.9 ⚪ M — Помесячная/погодовая инфляция (ряды вместо констант)
**PE:** инфляция по группам задаётся помесячно или по годам (ряд).
**У нас:** константная годовая ставка на группу (4 группы); группы «недвижимость/ОС» нет
(capex не индексируется).
**Работа:** `inflation_*` как ряд (год → ставка) + группа для ОС. Ядро уже строит индекс —
заменить источник.

## 2. Окружение и налоги

### 2.1 ✅ L — Настраиваемый налоговый блок (произвольные налоги)
**PE:** пользовательские налоги: название, ставка, база (продажи/прибыль/имущество/ФОТ/
произвольная формула), периодичность уплаты, куда относить (себестоимость/фин.результат/
прибыль).
**У нас:** фиксированный набор (прибыль, имущество, НДС, налог с продаж, взносы с ФОТ);
заготовка `Tax` в `models/environment.py` есть, но движком **не используется**.
**Сделано** (0.9.28, `CUSTOM-TAXES-DECOMPOSITION.md`): движок поверх заготовки —
базы revenue/payroll/property/profit/**formula** (по предварительному прогону, без
циклов), отнесение expense → I21 / profit → I24, периодичность месяц/квартал/год
(уплата в последнем месяце периода → C12, задолженность → B21), ошибка формулы —
отклонение расчёта, детализация C12 по налогам. UI — секция на вкладке «Проект».
«В себестоимость»/«в цену» — v2.

### 2.2 🟡 S — Учётная ставка ЦБ (нормирование процентов)
**PE:** ставка рефинансирования: проценты по займам вычитаемы в пределах норматива,
сверхнормативные — из прибыли.
**У нас:** флаг `interest_on_profit` вручную на весь заём; автоматического нормирования нет.
**Работа:** `cb_rate` в окружении + автоматический сплит процентов I18/I24 по нормативу
(ставка ЦБ × коэффициент).

### 2.3 ⚪ S — Периодичность уплаты налогов
**PE:** налоги платятся по своей периодичности (месяц/квартал/год) — влияет на кассу и `B21`.
**У нас:** все налоги платятся в месяце начисления (v0-упрощение, зафиксировано в SPEC).
**Работа:** параметр периодичности хотя бы для налога на прибыль и НДС; отсрочка → `B21`.

### 3.2 ✅ Сырьё и материалы как сущности — сделано (0.9.20, вместе с 1.1)

### 3.3 ✅ Сложные схемы оплаты продаж — сделано (0.9.24, PaymentTerms.schedule)

### 3.4 ✅ Пер-строчный НДС — сделано (0.9.25, SalesLine.vat_rate); «варианты продаж» = несколько строк на продукт (было)
**PE:** несколько вариантов реализации одного продукта; индивидуальные налоги строки сбыта.
**У нас:** несколько `SalesLine` на один `product_id` уже можно (варианты де-факто);
индивидуальных налогов строки нет (только глобальные ставки).
**Работа:** пер-строчная ставка НДС/налога с продаж (пищёвка 10% + прочее 20% в одном
проекте) — маленькое поле, заметная польза.

## 4. Результаты и анализ

### 4.1 ✅ Язык формул и «таблицы пользователя» — сделано (0.9.27)
**PE:** ключевая фича гибкости — ~40 функций над месячными рядами (Дисконтировать, IRR,
Сдвиг, Аккумулировать, Если, …), пользователь строит произвольные таблицы/показатели.
**У нас:** отсутствует полностью.
**Работа:** отдельная подсистема (как ревью): безопасный парсер/вычислитель выражений над
рядами результата + именованные пользовательские таблицы (хранятся в модели) + вкладка UI.
Открывает дорогу 2.1 (базы налогов формулой) и произвольной аналитике. Самая крупная
оставшаяся фича паритета.

### 4.2 ✅ M — Детализация результатов (drill-down строк отчётов)
**PE:** раскрытие агрегированной строки отчёта в составляющие (какие продукты/статьи её
сформировали).
**У нас:** отчёты отдаются готовыми строками без разбивки по источникам.
**Сделано** (пакет №6): `CalcResult.details` — слагаемые, сохранённые конвейером
(Σ = строка отчёта точно): I1/C1 по продуктам, C2/C3 по статьям, I16 по статьям
(вкл. штат), C14 по активам (вкл. этапы, выкуп лизинга); раскрытие строк в таблицах
результатов (работает вместе с агрегацией). I5/I6 не детализируются: пул готовой
продукции делает пер-строчную разбивку фейковой аллокацией.

### 4.3 ✅ M — Доходы участников (эффективность для инвестора/кредитора)
**PE:** денежные потоки каждого участника финансирования (акционер, кредитор): вложения,
изъятия (дивиденды/проценты/погашения), индивидуальные NPV/IRR.
**У нас:** только показатели проекта в целом.
**Сделано** (0.9.29, `PARTICIPANTS-DECOMPOSITION.md`): `CalcResult.participants` —
акционеры (−C21 + C26; equity-IRR с терминальной стоимостью B33) и каждый заём
(поток кредитора из графика движка, валютные — по FX; терминальная — непогашенное
тело; IRR полного займа = ставке — самопроверка). Карточка на сводке результатов +
таблица в DOCX. Кредитная линия автоподбора/лизингодатели — v2.

### 4.4 ✅ S — Анализ изменений (сравнение версий проекта)
**PE:** сравнение сохранённых версий одного проекта (что изменилось в данных/результатах).
**У нас:** нет версий модели (только `updated_at`); есть дубликат проекта и What-If.
**Сделано** (`PROJECT-VERSIONS-DECOMPOSITION.md`): таблица `project_versions`

### 4.5 ⚪ M — Доходы подразделений / структура компании

### 4.6 ⚪ S — Актуализация этапов (план-факт календарного плана)
