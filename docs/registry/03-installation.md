# Установка и эксплуатация

Платформа поставляется исходным кодом и собирается в контейнеры Docker. Всё ниже сверено
с `docker-compose.yml` и Dockerfile репозитория; настройки установки и решения владельца
— `docs/OWNER-SETUP.md`, перечень переменных — `backend/.env.example`.

## Состав установки

| Сервис | Что делает | Образ |
|---|---|---|
| `db` | СУБД PostgreSQL 16; данные — том `pgdata` | `postgres:16-alpine` |
| `db-setup` | при каждом старте заводит роль приложения `finans_app` без прав суперпользователя и передаёт ей базу; завершается | `postgres:16-alpine` |
| `redis` | брокер фоновых задач и хранилище их результатов | `redis:7-alpine` (см. `README.md`, п. 3) |
| `api` | сервер API; при старте применяет миграции схемы | сборка `backend/` |
| `worker` | фоновые задачи (Монте-Карло, чувствительность) | сборка `backend/` |
| `beat` | планировщик: сверка неоплаты, письма о деньгах, автопродление, акты, зависшие задачи | сборка `backend/` |
| `backup` | резервная копия базы раз в сутки, хранение `BACKUP_KEEP_DAYS` дней, проверка восстановления раз в `RESTORE_CHECK_DAYS` дней; том `backups` | `postgres:16-alpine` |
| `web` | раздача интерфейса и проксирование API (nginx), порт 8080 | сборка `frontend/` |

Ресурсы сервера зависят от числа пользователей и того, как часто считают Монте-Карло;
нагрузочная проверка не проводилась, и стартовую конфигурацию называет правообладатель:
`[заполняет правообладатель: проверенная конфигурация сервера]`.

## Установка

1. Сервер Linux с Docker и Docker Compose v2.
2. Получить исходный код (`git clone` репозитория правообладателя).
3. Создать `.env` рядом с `docker-compose.yml` по образцу `backend/.env.example`.
   **Обязательно** в продакшене: `APP_ENV=production`, `JWT_SECRET` (длинная случайная
   строка — без неё сервер в продакшене не стартует), `POSTGRES_PASSWORD` (суперпользователь
   базы — обслуживание и резервные копии), `APP_DB_PASSWORD` (роль приложения; без символов
   `@ : / ? # %` — пароль стоит в адресе подключения), `PUBLIC_URL`, `USAGE_SALT`. Остальное — по решениям владельца (почта, оплата, реквизиты продавца,
   юридические документы). Секреты живут только в `.env` на сервере.
4. `docker compose up -d --build`. Сервис `db-setup` заведёт роль приложения, `api`
   дождётся его, применит миграции (`alembic upgrade head`) от имени этой роли и
   поднимется; интерфейс — `http://<сервер>:8080`. **Приложение не подключается
   суперпользователем**: суперпользователь обходит политики изоляции организаций (RLS)
   всегда, и «Готовность» назовёт такую установку проблемой.
5. Проверить установку: `docker compose exec api python scripts/check_readiness.py` —
   по каждому пункту «что сейчас, что не работает, чем включить»; код выхода 1 при
   проблеме. Тот же отчёт — вкладка «Готовность» служебного раздела. Выключенное по
   решению владельца (почта, оплата) — «выключено», а не проблема.

## Первичная настройка

- **Сотрудник платформы** (доступ к служебному разделу) выдаётся только на сервере,
  маршрута в API нет: пользователь регистрируется обычным путём, затем
  `docker compose exec api python scripts/set_staff.py --email <адрес> --role operator`
  (`--role support` — только просмотр; `--list` — кто сейчас сотрудник).
- **Демо без регистрации** (кнопка на входе):
  `docker compose exec api python scripts/seed_demo.py --public` — пароли случайные и
  нигде не печатаются; повторный запуск не плодит дубликатов.
- **HTTPS** — на внешнем обратном прокси или балансировщике перед `web`; сертификат и
  домен — у владельца установки.

## Обновление

1. Резервная копия базы: `docker compose exec backup sh /ops/backup/backup.sh once`.
2. `git pull` нужной версии, `docker compose up -d --build`: миграции применятся при
   старте `api`. Принудительного или удалённого обновления у программы нет — версию
   меняет только владелец установки.
3. `check_readiness.py` после обновления.

Версия методики расчёта видна в интерфейсе и в каждом документе; если методика
менялась, планы, отправленные по ссылке раньше, говорят об этом посетителю сами.

## Резервные копии

Сервис `backup` (`ops/backup/backup.sh`) делает `pg_dump` раз в сутки в
`BACKUP_HOUR_UTC` часов по UTC; новая установка получает первую копию сразу. Копия
пишется во временный файл и получает имя только целой; старые (`BACKUP_KEEP_DAYS` дней)
удаляются только после успешной новой. Раз в `RESTORE_CHECK_DAYS` дней последняя копия
разворачивается в отдельную базу и читается (`ops/backup/restore-check.sh`) — копия,
которую ни разу не разворачивали, ничего не гарантирует. Итог — отметки в томе
`backups`, «Готовность» → «Резервные копии» читает их и называет проблему: копий не было,
последняя попытка не удалась (с причиной), копия старше суток, восстановление не
проверялось или не прошло.

- копия сейчас — `docker compose exec backup sh /ops/backup/backup.sh once`;
- проверка восстановления — `… backup.sh check`;
- восстановление: `pg_restore -d <новая база> /backups/finans-<время>.dump` от
  суперпользователя, затем `ops/db/app-role.sql` для роли приложения;
- **копии лежат на том же сервере** — вынесите копию на другую площадку в России
  (`docs/HOSTING-CHECKLIST.md`).

Копии делает суперпользователь базы: роль приложения под RLS видит только «свою»
организацию, и копия от её имени была бы пустой.

## Наблюдение за работой

- `docker compose logs api worker beat` — журналы сервисов; адрес ссылки для инвестора
  в журнал доступа не попадает (вычищается).
- **Трекер ошибок** (совместимый с Sentry) — `SENTRY_DSN`; без адреса выключен. Перед
  отправкой из события вычищаются тела запросов, куки, почта, токены и ключи.
- **Планировщик** оставляет след каждого запуска в служебном журнале — молчание журнала
  значит «не запускался», а не «всё хорошо»; зависшие задачи — письмом операторам при
  заданном `STUCK_JOB_ALERT_MINUTES`.
- **Журнал действий** каждой организации — у неё самой («Организация» → «Журнал
  доступа»).

## Остановка

`docker compose down` останавливает сервисы; данные остаются в томе `pgdata`.
**`docker compose down -v` удаляет том с базой** — без резервной копии это потеря всех
данных клиентов.
